# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Tanot" (แบรนด์เดิม OME) — a static site (no build step at deploy time, no `package.json`; the only server code is the Cloudflare-only Pages Functions under `functions/api/` — see "Cloudflare Pages backend" below) deployed two ways from the same source: **GitHub Pages** (`tanot713-sudo.github.io/My-Web-App` — the path is case-sensitive and follows the repo name; lowercase 404s, via `.github/workflows/deploy-pages.yml` on every push to `main`) and **Cloudflare Pages** (`my-web-app-5w2.pages.dev`, auto-deploys from the same repo). It's a personal toolbox: study tools (law/business/engineering classrooms), document tools (Word/Excel/PDF split, doc-check), an investment-education hub (12 sub-pages), a text-to-speech/speech-to-text page, a budget tracker, a 3D object sim, etc. Everything is vanilla ES5-leaning JS, no framework, no bundler — files are served as-is. The one exception is `languages.html`'s React app, which has a **local-only, pre-commit** build step — see "The `languages.html` React app" below — nothing about the deploy pipeline itself changes.

## Commands

There is no CI/deploy-time build/lint/test command — this is plain HTML/CSS/JS served directly. A `check` CI job runs `node --check` on every first-party `.js` file before `deploy` (see `.github/workflows/deploy-pages.yml`) — that's a syntax gate, not a build.

- **Test suite** (`tests/`, own `package.json` — never at root): `cd tests && npm ci && npx playwright install chromium`, then `node repo-guards.mjs` (bump `CACHE`, PRECACHE files exist, no file >25 MiB, `languages.compiled.js` matches `.jsx`, CDN/vendor libs listed in `credits.html`; base ref via `GUARD_BASE`, default `origin/main`), `npx playwright test ai.spec.js` (Phase 4 cloud AI, see below), `npx playwright test smoke.spec.js` (every menu page offline, no console errors, no horizontal overflow at 390px), `npx playwright test visual.spec.js` (baselines in `tests/__screenshots__`; refresh deliberately with `npm run test:update`; config pins full Chromium via `channel: 'chromium'` — the default headless-shell renders Thai text differently — plus `Asia/Bangkok` and a frozen clock, so local baselines match CI). Runs in CI on PRs and before deploy. Known-benign console errors are listed with reasons in `tests/helpers.js`; unlisted `credits.html` gaps are baselined in `repo-guards.mjs`.
- **Syntax-check a JS file before committing**: `node --check path/to/file.js`
- **Local server for manual/Playwright testing**: `python3 -m http.server <port>` from the repo root, then open `http://localhost:<port>/<page>.html`
- **Bypass the password gate when testing**: set `localStorage['tanot:auth'] = '1'` before loading a page (see Auth Gate below) — there is no real login flow to drive.
- **Testing is done ad hoc with Playwright** (browser automation), not an installed test suite — write a throwaway script under a scratch dir, seed `localStorage` with synthetic data for anything that would otherwise hit the network (most pages have a "demo data" fallback specifically to make this possible without real network access), screenshot at a few widths (~390/760/1100px) in both themes, and check for zero console/page errors.
- **Deploy verification**: after pushing to `main`, check the `deploy-pages.yml` workflow run for that commit's SHA via GitHub Actions (list workflow runs filtered to `event: workflow_dispatch` or `push`). The concurrency group is `pages` with `cancel-in-progress: false` — a stuck/`waiting` run (e.g. blocked on an environment protection rule) will silently queue-block every subsequent deploy until it's cancelled.

## Architecture

### Shared shell (every page wires these, in this order)
0. `theme-boot.js` — `<script src="theme-boot.js"></script>` in `<head>`, **not deferred**, immediately before the `theme.css` link (enforced by `tests/repo-guards.mjs`). It is the single owner of theme state: it sets `data-theme` (light/dark), `data-accent` (`teal` default, `blue`, `violet`, `orange`, `graphite`), `data-style` (`flat` default, `soft`, `outline`), `--ome-f` (`prompt` default or `ibmplex`) and `<meta name="theme-color">` before first paint (no dark-mode flash), migrates old stored values (9 accents / 8 styles / 6 fonts → the curated sets above), and exposes `window.OmeTheme` (`get`/`set`/`onChange`/`loadFont`). Keys: `localStorage['ome:theme'|'ome:accent'|'ome:style'|'ome:font']`. Don't read/write those keys anywhere else.
1. `auth-gate.js` — client-side-only password gate (SHA-256 hash check against `localStorage['tanot:auth']`). Explicitly **not real security**: anyone can bypass it via DevTools. It exists to keep casual/accidental visitors out, nothing more. It **no-ops on `*.pages.dev`**, where Cloudflare Access protects the whole domain (see "Cloudflare Pages backend" below); it only still gates GitHub Pages, and gets deleted (file + the 42 `<script>` tags + its `sw.js` PRECACHE entry) once GitHub Pages becomes a redirect (ROADMAP Phase 0a item 7).
2. `shell.js` — defines the *entire site's* navigation menu once (the `MENU` array, including the investment sub-nav that used to live in a separate `invest-nav.js`), renders the hamburger/drawer nav, the light/dark button and the settings panel (accent/style/language/font rows — it only holds display labels and calls `OmeTheme.set`). All pages import this the same way: `<script src="shell.js" defer></script>`.
3. `theme.css` — the single shared design-system stylesheet (theme v2, ROADMAP 0c). Structure: `@layer tokens, base, components, layouts` followed by an **unlayered compat section**. Layered rules always lose to a page's own `<style>`, and base/components/layouts are scoped with `:where([data-layout])`, so they only switch on for a page whose `<body>` carries `data-layout="tool|app|reader|dashboard|hub"` — pages not yet migrated render exactly as before (verified by the visual baselines). The compat section (shell nav/drawer/footer/settings, the `body.ome-tool-page` / `body.ome-app-page` remaps, `data-style` overrides for legacy `.card/.kpi/.btn`, the modal) is deliberately unlayered because it must beat page styles; delete pieces of it as pages migrate (ROADMAP Phase 2). Tokens: legacy `--ome-bg/card/ink/muted/line/brand*` stay (pages use them); v2 names (`--ome-surface-0/1/2`, `--ome-text-1/2/3`, `--ome-border`, `--ome-accent*`, `--ome-on-accent`, `--ome-ok|warn|err|info` + `-soft`/`-ink`, `--ome-radius-sm|md|lg|pill`, `--ome-shadow-1..3`, `--ome-z-*`, `--ome-dur-*`, `--ome-chart-1..8|up|down|grid|axis`) derive from them. Central components (class names match what legacy pages already use, so a migrated page just deletes its own copy): `.btn` (default/`.primary`/`.ghost`/`.danger` × `.sm`/default/`.lg`, `.icon`), `.card`/`.card-head`, `.field`/`.frow`, `.table-wrap`/`.table`, `.badge`/`.chip`, `.tabs`/`.tab`, `.segmented`, `.kpi-grid`/`.kpi`, `.toolbar`, `.empty`, `.toast-region`/`.toast`, `<dialog class="dialog">`, `.list`/`.list-row`; layout helpers `.page`, `.page-head`, `.stack`, `.row`, dashboard `.grid` + `.span-N`, hub `.tiles`/`.tile`, reader `.prose`. `theme-preview.html` shows all of them. Added with the invest family migration (Phase 2 round 2): `.callout` (`ok|warn|err|info`), `.kv`, `.status`, `.step`, `details.disclosure`, `.crumb`, `.subnav` (two-level section nav), `.chk-list`/`.yn-row` (+ `.segmented > .yes/.no`), `.table.right`, `.mini`/`.log-*`, `.chart-wrap`/`.chart-cap`, `.cmp`, `.tranche`, `.light`, `.badge.wrap`; the in-card vertical rhythm (`.card > * + *`) is scoped to `body[data-invest-key]` so already-migrated pages don't shift. Every chart on the invest pages takes its colors from `chart-theme.js` (canvas charts via `lightweight()`/`candles()`, JS-built SVG via `get()` + redraw on `onChange`) — never hardcode a chart hex.

Also part of theme v2 but opt-in per page: `icons.svg` (Lucide sprite, `<svg class="ome-icon"><use href="icons.svg#i-house"/></svg>`; to add icons, run `node tests/build-icons.mjs name1,name2` (keeps existing icons, pulls from the pinned `lucide-static` devDependency) rather than hand-pasting paths) and `chart-theme.js` (`window.OmeChartTheme`: `get()`, `lightweight()`, `candles()`, `chartjs(Chart)`, `echarts()`, `onChange(fn)` — reads the `--ome-chart-*` tokens, resolved to `rgb()`, and fires on theme/accent/font changes). The 8 chart colors are a fixed, CVD-validated order: never cycle past 8, never reuse status colors as series colors.

`palette.js` (Ctrl/⌘+K or the search button `shell.js` puts on the nav; lazy-loaded on first use) searches `window.OME_MENU` plus commands, and `quick-add.js` (`OmeQuickAdd.open({type})`) appends to `budget:records` and fires `tanot:quickadd`; both inject their own DOM and are styled by the unlayered `.ome-pal`/`.ome-qa` rules at the end of `theme.css`, so they work on pages that haven't migrated to a `data-layout`. `index.html`/`index.js` is the "วันนี้" dashboard (`data-layout="dashboard"`): read-only, no network, reads other pages' data through `TanotData.read/raw/readIdb/onChange` and re-renders on `tanot:data`/`tanot:quickadd`/`storage` — the key shapes it reads are listed in the header of `index.js`; if a page changes the shape of a key listed there, update the dashboard too.

Pages that are PWA-installable also register `sw.js` (see below) via `shell.js`.

### Service worker / cache versioning (`sw.js`)
Network-first for HTML, cache-first for other same-origin assets. `PRECACHE` lists every file that should work offline. **Whenever you add or change a JS/HTML file that's cache-first, you must bump the `CACHE` const version string** (`ome-vNNN`) or returning users keep serving stale code indefinitely — this is the single most common way a "fix" silently fails to ship. Heavy vendored libraries (`vendor/transformers/*`, `vendor/firebase/*`) are intentionally left out of `PRECACHE` and instead lazy-cached on first real use, so visitors who never touch those tools don't pay for a multi-MB download.

### Per-tool pages
Each tool is a `<name>.html` + `<name>.js` pair (occasionally split further, e.g. `doc-check.html` / `doc-check-file.html`). There's no router or shared app shell beyond the nav — navigation between tools is a plain page load. Investment tools (`invest-*.html/js`) are the largest family (12 pages) and were built by cloning the most similar existing page and adapting it (e.g. `invest-global-stock.*` is a clone of `invest-thai-stock.*` with `.BK` suffix removed; `invest-baac-lottery.*` is a near-byte-identical clone of `invest-gsb-lottery.*`) — when adding a new tool in an existing family, find the closest sibling and diff against it rather than designing from scratch.

Common conventions across tool pages:
- **localStorage namespacing**: everything is prefixed `tanot:<feature>:<key>` (e.g. `tanot:invest:thstock`, `tanot:tts:gcloudkey`). Check for existing keys before picking a new one — collisions between two tools sharing a prefix have caused real bugs before.
- **Client-side-only, no backend**: any "fetch a live value" feature (stock/crypto/gold prices, FX rates, news) has to route around CORS via a proxy chain since there's no server to proxy through. The **first** proxy tried everywhere is the site's own: each file's `OWN_PROXY` constant resolves to the same-origin Pages Function `/api/proxy?url=` on `*.pages.dev` (`functions/api/proxy.js`, allowlists only the 4 hosts this site actually needs: Yahoo Finance, Google News, alternative.me), and to the legacy hand-deployed Worker `tanot-cors-proxy.tanot713.workers.dev` everywhere else (i.e. GitHub Pages; original source kept at `docs/cors-proxy-worker-original.js`, removed once GitHub Pages becomes a redirect). After it, the chain falls through several public proxies (`allorigins`, `codetabs`, `cors.eu.org`, `test.cors.workers.dev`, `api.cors.lol`) as a backup, then a direct-fetch last resort. Those public proxies are unreliable and rotate — `corsproxy.io` went paid-only, `thingproxy.freeboard.io`'s DNS died, `proxy.corsfix.com` needs the domain pre-registered on their dashboard (all three were tried and removed in 2026-09) — which is exactly why the owned Worker now leads the chain instead of depending on them. Every such fetch still has a `localStorage` cache-with-timestamp fallback and a "paste/type it in yourself" manual fallback, and must never render a hard error state; degrade to stale-cache or manual-entry instead. If the own proxy ever needs a new allowed host, edit `ALLOWED_HOSTS` in `functions/api/proxy.js` (deploys with the site); the legacy Worker would need a hand redeploy by the owner, so don't bother unless GitHub Pages still needs it. If public proxies break again, check each candidate's live status via WebSearch before wiring it in (a proxy can look fine in search results yet fail with `ERR_NAME_NOT_RESOLVED` for real users — regional DNS blocks are common in Thailand).
- **Google Drive sync** (`DriveSync` pattern, repeated per-tool with a different `DRIVE_FILE_NAME`) is opt-in, best-effort backup of a tool's local data to the user's own Drive — not a sync-of-record.
- **Firebase Realtime Database sync** (`firebase-sync.js`, currently only used by `budget.html` via `FirebaseSync.connect('budget', ...)`) requires Google sign-in and scopes every user's data under `<basePath>/<uid>/...`. The enforced Security Rules live in the Firebase Console (project `tanot-budget`), **not** in this repo's deploy pipeline — there is no Firebase CLI/CI wired up here, so `database.rules.json` at the repo root is a **manually-synced mirror for review/history only**. If you change the rules, you must paste the same JSON into Firebase Console → Realtime Database → Rules → Publish yourself; editing `database.rules.json` alone does nothing live. Keep the two in sync by hand whenever either changes.
- **Risk/finance tools carry real disclaimers** — these are educational calculators, not financial advice, and the copy says so explicitly. Preserve that framing when extending them.
- **No explainer clutter in the UI — absolute rule, not a default, applies to every page in this repo, not just `invest-*`.** Never add a "เรียนรู้"/"Learn" accordion card, a head-sub subtitle line under the `<h1>`, a disclaimer paragraph, a static hint/caption span next to a button or input row explaining how to use it, a keyboard-shortcut/mouse-gesture cheat-sheet paragraph, "how this works" narration, step-by-step walkthroughs, or any other explanation of a function/feature into a page's visible copy **unless the user explicitly asks for it in that message**. This is not "use judgment about how much to explain" — it is "write zero explanatory copy by default, every time, on every page, including brand-new pages and pages you are only touching for an unrelated reason (e.g. a layout change) — check for this content and remove it on sight even if removing it wasn't the task you were asked to do." Every `invest-*` page had its head-sub subtitle, "เรียนรู้"/"Learn" lesson accordion(s), and footer disclaimer paragraph deliberately stripped out (Sept 2026, one commit per page — see git log), and `cad.html`/`cad.js` got the same sweep (Sept 2026): head-sub subtitle, the `.cad-precise-hint` spans next to every precise-input row (distance/angle, array, text, hatch, block-insert), the "draw a closed shape then click this" hint under the quick-extrude button, the keyboard/mouse cheat-sheet paragraph at the bottom of the 2D panel, the constraint-panel and plot-panel hint paragraphs, the "Stage 9 (proof of concept)" warn-note banner, and four instructional paragraphs in the 3D panel (add-shape workflow, steps-list workflow, 3D-viewport controls, export-format explainer) — along with roughly two dozen fully orphaned/unused `*Hint` i18n keys that were dead code left over from an earlier iteration. Do not reintroduce any of this, even a shortened version, even if it seems genuinely helpful, on any page, unless the user explicitly instructs you to add it back in that message. This does not apply to dynamic, state-dependent feedback that only exists because of what the user is doing right now (a "click the first corner" prompt during an active multi-click sketch, a validation error, an empty-state message, a live warning that only appears when a real problem is detected) — that stays, because it's functional feedback, not a static tip. The one other narrow exception that survived the sweep is a card that carries live functional data rather than static explanation (e.g. the gold page's factors card with its DXY/TNX price chips, or the business page's reference-ideas list) — those stay because removing them would delete a feature, not an explanation; anything that is purely descriptive text about how a tool works still goes. Where a tool genuinely needs a one-line risk disclaimer and the user has asked for that framing, keep it to one short line; anything longer describing internals (e.g. "this score is a simple heuristic that does X, Y, Z...") gets cut entirely, not shortened-in-place. When in doubt, delete the sentence rather than trim it or keep it "just in case."

### Cloudflare Pages backend (`wrangler.toml`, `functions/api/*`, `migrations/*`)
The Cloudflare Pages deploy (not GitHub Pages) has server code: **Pages Functions** under `functions/api/` (only `/api/*` invokes them; everything else stays static). `wrangler.toml` at the root is the source of truth for Pages config — once it exists Cloudflare **ignores** the bindings and plain-text vars set in the dashboard, so `OWNER_EMAIL` / `ACCESS_AUD` / `TEAM_DOMAIN` live in its `[vars]`, plus bindings `DB` (D1 `tanot-db`), `FILES` (R2 `tanot-files`), `AI` (Workers AI). **Secrets (`ANTHROPIC_API_KEY`) stay dashboard-only — never put a secret in `wrangler.toml` or any file; the repo is public.** **Never add a root `package.json`** (Pages would run `npm install` on every build) — which is also why Functions call the Anthropic API with plain `fetch` rather than the SDK.
- **Auth**: Cloudflare Access (Zero Trust, owner's email only) guards the whole `my-web-app-5w2.pages.dev` domain. `functions/api/_middleware.js` re-verifies the Access JWT on every `/api/*` request (signature via `https://<TEAM_DOMAIN>/cdn-cgi/access/certs`, `aud`, `iss`, expiry, email == `OWNER_EMAIL`) and fails closed, so paid endpoints don't depend solely on dashboard config. There are no client-side passwords for paid features any more.
- **Endpoints**: `proxy.js` (CORS proxy, GET), `ai/chat.js` · `ai/summarize.js` · `ai/embed.js` · `ai/usage.js` (Workers AI — see "Cloud AI" below), `asr.js` (Whisper via `env.AI`), `ocr.js` (Claude Vision OCR — its transcription prompt is deliberately strict about *not* fixing typos; keep it verbatim), `session.js` (used by `sw.js` to tell an Access-expired redirect apart from Pages' own `.html` → clean-URL redirects). Original hand-deployed Worker sources are in `docs/*-original.js` for reference only.
- **Pages-only features**: `/api/*` doesn't exist on GitHub Pages, so client code gates cloud features on `/\.pages\.dev$/.test(location.hostname)` and hides the option elsewhere (see `doc-check.js`, `text-to-speech.js`).
- **`sw.js` + Access**: never cache/intercept `/api/` or `/cdn-cgi/`; only cache `ok` + `basic` HTML; on an Access-expired navigation serve the cached page with a "re-login" bar (link carries `?relogin=1`, which the SW passes straight to the network). Manifest links use `crossorigin="use-credentials"` so the manifest fetch carries the Access cookie.
- **D1 schema**: `migrations/0001_init.sql` (idempotent `IF NOT EXISTS`, pasted into the D1 console by the owner). Add schema changes as new numbered files; never edit an applied migration.

### Cloud AI (ROADMAP Phase 4: `ai-client.js`, `functions/api/ai/*`, `functions/_lib/ai.js`)
Cloud first, in-browser model as the offline fallback. `functions/api/ai/`: `chat` (POST, SSE stream normalized to `data:{"t":…}` … `data:{"done":true,…}`), `summarize` (POST, non-stream, result cached in D1 `ai_cache`, key = sha256 of task+model+messages so identical input is free and changed numbers re-summarize; `refresh:true` bypasses), `embed` (bge-m3), `usage` (GET). `model: 'main'` = `@cf/aisingapore/gemma-sea-lion-v4-27b-it` (default, best Thai), `'fast'` = `@cf/qwen/qwen3-30b-a3b-fp8`. Shared helpers live in `functions/_lib/ai.js` (no `onRequest*` export ⇒ not a route). Things that are easy to break:
- **Quota**: every call adds to `ai_usage` (UTC day, per kind); `asr.js` writes its Whisper neurons there too (one shared free pool of 10,000/day, ceiling = `AI_DAILY_NEURONS` in `wrangler.toml [vars]`). Requests are refused with 429 `{code:'quota'}` *before* the model runs if the estimate would exceed the ceiling; cache hits are checked first and cost nothing. Neurons-per-token rates in `MODELS` are unverified estimates (Cloudflare docs were unreachable when written) — tune them there only.
- **Messages are normalized server-side** (`prepareMessages`): leading system messages merge into one, a system "reminder" placed after the conversation moves onto the last user message, adjacent same-role messages merge. Gemma-style chat templates reject multiple/late system messages, but the pages send them (local-model habit) — don't remove this. Qwen3 gets `/no_think` appended and `<think>` blocks are stripped.
- **Client**: `ai-client.js` (`window.AiClient`: `available()` = `*.pages.dev` or `window.TANOT_AI={enabled}` for tests; `chat/summarize/embed/usage/asr/ocr`; errors carry `code` and `AiClient.canFallback(err)` says whether to drop to the local model). `shell.js` injects it before `ai-chat-widget.js`; the invest pages and `text-to-speech.html` load it with a plain `<script>`. Pattern in pages: `AiClient.available()` → cloud → on `canFallback` error and `!isIOS()` run the old local-worker path; iPhone never falls back (local models can't run there) and shows `AiClient.friendlyMessage(err)`. On GitHub Pages nothing changes (no `/api`), so the old iOS "not supported" gate stays there.
- **Cache migration**: on `*.pages.dev` the stock/gold/bitcoin/commodities summaries use D1 `ai_cache` and never touch Firebase; `ai-summary-cache.js` (public-write Firebase) is now reached only from GitHub Pages and goes away with it.
- Meeting summary (`text-to-speech.js`): whole transcript in one `summarize` call up to 40,000 chars, above that chunks on `fast` + a final `main` pass; the browser map-reduce is `localMeetingSummary`. Transcripts leave the device on this path (Whisper cloud already did).
- Tests: `tests/ai.spec.js` runs the real functions against `tests/sync-server.mjs` (port 8126) with a fake `env.AI` (`/__ai?mode=ok|quota|down`, `/__ai?limit=N`, `/__ailog`).

### Data layer / sync (ROADMAP Phase 1: `data-registry.js`, `tanot-data.js`, `functions/api/sync.js`)
Every page loads `<script src="data-registry.js"></script><script src="tanot-data.js"></script>` right after `theme-boot.js` in `<head>`, not deferred (enforced by `tests/repo-guards.mjs`). Page data stays where it always was (localStorage / the page's own IndexedDB); `tanot-data.js` patches `Storage.prototype` and `IDBObjectStore.prototype` to track changes and syncs diffs with D1 `docs` via `GET/POST /api/sync` (last-write-wins per doc, max 40 docs per POST). It is **inert everywhere except `*.pages.dev`** (tests enable it with `window.TANOT_SYNC = { enabled: true }`).
- **Adding a new storage key**: add a rule in `data-registry.js` - `kind: 'sync' | 'local' | 'cache'`; for sync, `mode: 'blob'` (default), `'list'` (JSON array of objects with a unique `idField` - concurrent adds from two devices merge) or `'map'` (JSON object, one doc per property). Anything holding an API key the UI promises stays on-device must be `'local'`. Unmatched keys default to `'local'`. New IndexedDB stores go in `IDB` with the exact schema the page creates; never list an `autoIncrement` store in `sync` (each device counts 1,2,3… so different records collide on the same id - `idbSynced()` refuses them; `report-dashboard`'s `reports` is migrate/backup-only for this reason).
- Safety rules the code relies on (don't break them): a page writing stale in-memory state is 3-way merged at `setItem` (list/map keys) so it can't delete items that arrived from another device; `IDBObjectStore.clear()` on a synced store puts back any record that was in the store but that this page never read (`getAll`) or wrote - e.g. one another tab pulled in; any never-synced/unsynced local value replaced by a remote one is copied to the `history` store (restorable on `data.html`); `localStorage.clear()` and "most keys vanished at once" never produce tombstones - they trigger a re-pull instead; imports (`migrate.html`, `data.html`) never write until the user presses import, stash the imported snapshot + every replaced value first, then read back and verify.
- The dirty queue (`localStorage['tanot-sync:dirty']`) is shared by all tabs: always read-modify-write it, never cache it in memory, and only clear an entry if its timestamp is unchanged since you read it.
- `budget.html` doesn't start Firebase sync when `TanotData.enabled` (Firebase delivers the whole array and would delete records that came via D1); Firebase stays GitHub Pages-only.
- `migrate.html` (pages.dev) opens `migrate-export.html` on github.io as a **popup** (not iframe - storage partitioning) and receives a snapshot via origin-pinned `postMessage`. The export side is read-only; it only adds a `tanot:migrate:exported` marker.
- `drive-backup.js` = one daily snapshot file in Drive (`OME_Progress/tanot-backup-YYYY-MM-DD-<device>.json`, one per device so two devices backing up the same day don't overwrite each other), same format as the migration snapshot. The per-page DriveSync copies, `firebase-sync.js`, `ai-summary-cache.js` and `vendor/firebase` stay until both devices have migrated (GitHub Pages still depends on them).
- Read API for aggregate pages: `TanotData.read(key, dflt)` (parsed JSON), `raw(key)`, `readIdb(db, store, {last:N})` (no write tracking, `[]` if the DB/store doesn't exist; `last` reads only the N newest records via cursor) and `onChange(fn)` — use these instead of `localStorage.getItem` so reading a key doesn't count as "the page read it" (which would pop the reload bar when remote data arrives).
- Tests: `tests/sync-server.mjs` runs the real `functions/api/sync.js` on `node:sqlite` with `migrations/*.sql`; `sync.spec.js` (2 browser contexts) and `migrate.spec.js` (127.0.0.1 = "github.io", localhost = "pages.dev").

### The `languages.html` React app (`languages.jsx` / `languages.compiled.js` / `build-languages.sh`)
Unlike every other page, `languages.html` is a React 18 app (React/ReactDOM still loaded as UMD globals from `unpkg.com`, unchanged). It used to run `@babel/standalone` in the browser on every page load to transpile a ~18,000-line inline `<script type="text/babel">` block — measurably slow, especially on phones. That inline block has been extracted to **`languages.jsx`** (the JSX source you actually edit) and is pre-compiled locally with esbuild into **`languages.compiled.js`** (plain ES2019, classic `React.createElement` runtime, committed to the repo like any other static file). `languages.html` just does `<script src="languages.compiled.js"></script>` — no Babel, no runtime JSX transform, nothing in the deploy pipeline changed.

**You must run `./build-languages.sh` and commit the resulting `languages.compiled.js` together with any edit to `languages.jsx`.** Editing `languages.jsx` alone does nothing live — the browser never loads that file, only `languages.compiled.js`. This is the same failure class as forgetting to bump `sw.js`'s `CACHE` version: an easy-to-forget manual step where the fix silently doesn't ship. The script requires Node (`npx esbuild ...`, no install/lockfile needed) and ends with `node --check` on its own output as a sanity gate.

Everything else about `languages.html` is unchanged: the `<script id="*-data" type="application/json">` blocks (vocab/phrases/script-writing data per language) still live directly in the HTML and are read via `document.getElementById(...).textContent` — only the JSX component code moved out.

### Heavy client-side ML (`text-to-speech.html` / `text-to-speech.js` / `tts-worker.js`)
Text→speech uses `facebook/mms-tts-*` via `vendor/transformers/` (Transformers.js + onnxruntime-web, self-hosted, not CDN-loaded — a prior CDN-based bare-specifier resolution bug inside a Worker is why the vendored bundle's imports were rewritten to relative paths). The onnxruntime-web runtime files (`ort-wasm-simd-threaded*.mjs/.wasm`, `ort.webgpu.bundle.min.mjs`, `onnxruntime-common/*`) are **pinned to 1.24.3** on purpose — 1.25+ has a confirmed upstream bug (`TransposeDQWeightsForMatMulNBits`, microsoft/onnxruntime#28306) that breaks session creation for some quantized models including Whisper. Don't bump these without first confirming that issue is fixed in the target version. Synthesis runs in a **pool of persistent Web Workers** (`tts-worker.js`, spawned via `getTtsWorkerPool()`), not the main thread, because single-thread WASM synthesis is fully synchronous and would otherwise freeze the page. Key things that look like they'd be free performance wins but were tried and reverted after real-world measurement: WebGPU backend (slower — immature quantized-op kernels), multi-threaded WASM via COOP/COEP cross-origin isolation (slower/same — thread oversubscription across the worker pool). The one that *did* help: staggering worker dispatch so only the first worker downloads the model initially (`pipeline-ready` message), avoiding N workers redundantly re-downloading the same multi-MB model on a cold cache. Speech→text uses Whisper, also via Transformers.js.

### Document tooling (`doc-check.js`)
Client-side file text-extraction already exists here and is the template to reuse for any other "read a file into text" feature: `.txt` via `file.text()`, `.docx` via `mammoth.js`, `.pdf` (with a text layer) via `pdf.js`, images via `Tesseract.js` OCR (`eng+tha`). Grammar/spell-check goes through the public LanguageTool API — note that LanguageTool has **no Thai support** (`ltCode: null` for `th`), so that feature is English-only; Thai text only gets light normalization, not real proofreading. Scanned (image-only) PDF pages are currently detected but not yet OCR'd — doing so would mean rendering each page to a canvas via `pdf.js` and feeding that canvas to Tesseract.js.

### 3D tooling (`sim-objects.js`)
Self-hosted Three.js (`vendor/three/`, including a `jsm/` mirror of the addons ESM modules) + GSAP + `three-mesh-bvh`/`three-bvh-csg` (vendored UMD builds) for boolean mesh operations. Personal model library persists to IndexedDB, not localStorage (binary model data).
