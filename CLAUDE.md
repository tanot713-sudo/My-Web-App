# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Tanot" (แบรนด์เดิม OME) — a static site (no build step at deploy time, no `package.json`; the only server code is the Cloudflare-only Pages Functions under `functions/api/` — see "Cloudflare Pages backend" below) served from **Cloudflare Pages** (`my-web-app-5w2.pages.dev`, auto-deploys from the repo, behind Cloudflare Access). **GitHub Pages** (`tanot713-sudo.github.io/My-Web-App` — the path is case-sensitive and follows the repo name) is **redirect-only** since 2026-10-02: the `deploy` job in `.github/workflows/deploy-pages.yml` runs `.github/scripts/github-pages-redirect.mjs`, which publishes a stub per `.html` that redirects to the same page on pages.dev, a 404 that redirects any other path, a `sw.js` that unregisters the old service worker, and the real `migrate-export.html` (+ the scripts it loads) because github.io's localStorage can only be read from that origin. Change `TARGET` in that script if the site moves to a custom domain. It's a personal toolbox: study tools (law/business/engineering classrooms), document tools (Word/Excel/PDF split, doc-check), an investment-education hub (12 sub-pages), a text-to-speech/speech-to-text page, a budget tracker, a 3D object sim, etc. Everything is vanilla ES5-leaning JS, no framework, no bundler — files are served as-is. The one exception is the four React pages (`languages`, `legal`, `classroom-business`, `classroom-engineering`), which have a **local-only, pre-commit** build step (`./build-react.sh`) — see "The 4 React pages" below — nothing about the deploy pipeline itself changes.

## Architecture

### Shared shell (every page wires these, in this order)
0. `theme-boot.js` — `<script src="theme-boot.js"></script>` in `<head>`, **not deferred**, immediately before the `theme.css` link (enforced by `tests/repo-guards.mjs`). It is the single owner of theme state: it sets `data-theme` (light/dark), `data-accent` (`teal` default, `blue`, `violet`, `orange`, `graphite`), `data-style` (`flat` default, `soft`, `outline`), `--ome-f` (`prompt` default or `ibmplex`) and `<meta name="theme-color">` before first paint (no dark-mode flash), migrates old stored values (9 accents / 8 styles / 6 fonts → the curated sets above), and exposes `window.OmeTheme` (`get`/`set`/`onChange`/`loadFont`). Keys: `localStorage['ome:theme'|'ome:accent'|'ome:style'|'ome:font']`. Don't read/write those keys anywhere else.
1. `shell.js` — defines the *entire site's* navigation menu once (the `MENU` array, including the investment sub-nav that used to live in a separate `invest-nav.js`), renders the hamburger/drawer nav, the light/dark button and the settings panel (accent/style/language/font rows — it only holds display labels and calls `OmeTheme.set`). All pages import this the same way: `<script src="shell.js" defer></script>`.
2. `theme.css` — the single shared design-system stylesheet (theme v2, ROADMAP 0c). Structure: `@layer tokens, base, components, layouts` followed by an **unlayered compat section**. Layered rules always lose to a page's own `<style>`, and base/components/layouts are scoped with `:where([data-layout])`, so they only switch on for a page whose `<body>` carries `data-layout="tool|app|reader|dashboard|hub"` — a page without `data-layout` renders exactly as before (every page has migrated since ROADMAP Phase 2 round 6, so this only matters for new pages). The compat section (shell nav/drawer/footer/settings, `data-style` overrides for legacy `.card/.kpi/.btn`, the modal) is deliberately unlayered because it must beat page styles; delete pieces of it as pages migrate (ROADMAP Phase 2). Tokens: legacy `--ome-bg/card/ink/muted/line/brand*` stay (pages use them); v2 names (`--ome-surface-0/1/2`, `--ome-text-1/2/3`, `--ome-border`, `--ome-accent*`, `--ome-on-accent`, `--ome-ok|warn|err|info` + `-soft`/`-ink`, `--ome-radius-sm|md|lg|pill`, `--ome-shadow-1..3`, `--ome-z-*`, `--ome-dur-*`, `--ome-chart-1..8|up|down|grid|axis`) derive from them. Central components (class names match what legacy pages already use, so a migrated page just deletes its own copy): `.btn` (default/`.primary`/`.ghost`/`.danger` × `.sm`/default/`.lg`, `.icon`; สถานะกด `.on`/`.active`/`[aria-pressed=true]`), `.spinner`, `.card`/`.card-head`, `.field`/`.frow`, `.table-wrap`/`.table`, `.badge`/`.chip`, `.tabs`/`.tab`, `.segmented`, `.kpi-grid`/`.kpi`, `.toolbar`, `.empty`, `.toast-region`/`.toast`, `<dialog class="dialog">`, `.list`/`.list-row`; layout helpers `.page`, `.page-head`, `.stack`, `.row`, dashboard `.grid` + `.span-N`, hub `.tiles`/`.tile`, reader `.prose`. `theme-preview.html` shows all of them. Added with the invest family migration (Phase 2 round 2): `.lang-toggle` (สลับ ไทย/EN, also reused for 2-way engine switches) + `.crumb .sep`, `.dropzone` (round 4: file drop/pick area), `.callout` (`ok|warn|err|info`), `.kv`, `.status`, `.step`, `details.disclosure`, `.crumb`, `.subnav` (two-level section nav), `.chk-list`/`.yn-row` (+ `.segmented > .yes/.no`), `.table.right`, `.mini`/`.log-*`, `.chart-wrap`/`.chart-cap`, `.cmp`, `.tranche`, `.light`, `.badge.wrap`; the in-card vertical rhythm (`.card > * + *`) is scoped to `body[data-invest-key]` so already-migrated pages don't shift. Every chart on the invest pages takes its colors from `chart-theme.js` (canvas charts via `lightweight()`/`candles()`, JS-built SVG via `get()` + redraw on `onChange`) — never hardcode a chart hex.

Also part of theme v2 but opt-in per page: `icons.svg` (Lucide sprite, `<svg class="ome-icon"><use href="icons.svg#i-house"/></svg>`; to add icons, run `node tests/build-icons.mjs name1,name2` (keeps existing icons, pulls from the pinned `lucide-static` devDependency) rather than hand-pasting paths) and `chart-theme.js` (`window.OmeChartTheme`: `get()`, `lightweight()`, `candles()`, `chartjs(Chart)`, `echarts()`, `onChange(fn)` — reads the `--ome-chart-*` tokens, resolved to `rgb()`, and fires on theme/accent/font changes). The 8 chart colors are a fixed, CVD-validated order: never cycle past 8, never reuse status colors as series colors.

`palette.js` (Ctrl/⌘+K or the search button `shell.js` puts on the nav; lazy-loaded on first use) searches `window.OME_MENU` plus commands, and `quick-add.js` (`OmeQuickAdd.open({type})`) appends to `budget:records` and fires `tanot:quickadd`; both inject their own DOM and are styled by the unlayered `.ome-pal`/`.ome-qa` rules at the end of `theme.css`, so they work on pages that haven't migrated to a `data-layout`. `index.html`/`index.js` is the "วันนี้" dashboard (`data-layout="dashboard"`): read-only, no network, reads other pages' data through `TanotData.read/raw/readIdb/onChange` and re-renders on `tanot:data`/`tanot:quickadd`/`storage` — the key shapes it reads are listed in the header of `index.js`; if a page changes the shape of a key listed there, update the dashboard too.

Pages that are PWA-installable also register `sw.js` (see below) via `shell.js`.

### Service worker / cache versioning (`sw.js`)
Network-first for HTML, cache-first for other same-origin assets. It also handles Web Push (`push`/`notificationclick`/`pushsubscriptionchange` — see "Web Push + reminders" below). `PRECACHE` lists every file that should work offline. **Whenever you add or change a JS/HTML file that's cache-first, you must bump the `CACHE` const version string** (`ome-vNNN`) or returning users keep serving stale code indefinitely — this is the single most common way a "fix" silently fails to ship. Heavy vendored libraries (`vendor/transformers/*`, `vendor/firebase/*`) are intentionally left out of `PRECACHE` and instead lazy-cached on first real use, so visitors who never touch those tools don't pay for a multi-MB download.

### Per-tool pages
Each tool is a `<name>.html` + `<name>.js` pair (occasionally split further, e.g. `doc-check.html` / `doc-check-file.html`). There's no router or shared app shell beyond the nav — navigation between tools is a plain page load. `electrical.html` (เครื่องคำนวณไฟฟ้า) is split three ways: `electrical-calc.js` holds every formula/table/standard citation with no DOM (UMD — `window.ElecCalc` in the page, `require()`d directly by `tests/electrical.spec.js`), `electrical.js` only reads inputs and renders; keep new formulas in the calc file with their units and source in the comment, and add a known-answer test for each. `tax.html` (ภาษีเงินได้) follows the same split: `tax-calc.js` (UMD, `window.TaxCalc`, no DOM) holds only the calculation order (expenses → deductions → retirement-group 500,000 cap → donations → progressive/minimum tax, plus `room`/`useful`/`simulate` for the "ถ้าซื้อเพิ่ม" tab); every number — brackets, caps, expense rates, deadlines — lives in `tax-rules/<ปีภาษี พ.ศ.>.json`, listed in `tax-rules/index.json`, with expired measures set to `null` (the field then hides). A new tax year = copy the latest JSON, edit, add it to `index.json` + `sw.js` PRECACHE + a known-answer test; never hardcode a cap in JS. The page reads budget income (income category → 40(1)/(2)/(8) via `tanot:tax:catmap`, default only `cat-salary` counts), insurance premiums (`InsuranceCalc.taxSummary` when `tanot:insurance:policies` exists — it lazy-loads `insurance-calc.js` — else `tanot:insurance:taxsummary`; only the `raw` amounts are used, caps come from the year JSON) and RMF/SSF/ThaiESG purchases from `tanot:invest:thaifund`; typed values (`tanot:tax:years`, sync map per year) override pulled ones. Investment tools (`invest-*.html/js`) are the largest family (12 pages) and were built by cloning the most similar existing page and adapting it (e.g. `invest-global-stock.*` is a clone of `invest-thai-stock.*` with `.BK` suffix removed; `invest-baac-lottery.*` is a near-byte-identical clone of `invest-gsb-lottery.*`) — when adding a new tool in an existing family, find the closest sibling and diff against it rather than designing from scratch.

Common conventions across tool pages:
- **localStorage namespacing**: everything is prefixed `tanot:<feature>:<key>` (e.g. `tanot:invest:thstock`, `tanot:tts:gcloudkey`). Check for existing keys before picking a new one — collisions between two tools sharing a prefix have caused real bugs before.
- **Client-side-only, no backend**: any "fetch a live value" feature (stock/crypto/gold prices, FX rates, news) has to route around CORS via a proxy chain since there's no server to proxy through. The **first** proxy tried everywhere is the site's own: each file's `OWN_PROXY` constant resolves to the same-origin Pages Function `/api/proxy?url=` on `*.pages.dev` (`functions/api/proxy.js`, allowlists only the 4 hosts this site actually needs: Yahoo Finance, Google News, alternative.me), (GitHub Pages is redirect-only now, so the invest pages' fallback to the old `tanot-cors-proxy` Worker is dead code — that Worker was deleted on 2026-10-02 and the leftover names in the invest code are intentionally not touched yet; its original source is kept at `docs/cors-proxy-worker-original.js` for reference only). After it, the chain falls through several public proxies (`allorigins`, `codetabs`, `cors.eu.org`, `test.cors.workers.dev`, `api.cors.lol`) as a backup, then a direct-fetch last resort. Those public proxies are unreliable and rotate — `corsproxy.io` went paid-only, `thingproxy.freeboard.io`'s DNS died, `proxy.corsfix.com` needs the domain pre-registered on their dashboard (all three were tried and removed in 2026-09) — which is exactly why the owned proxy leads the chain instead of depending on them. Every such fetch still has a `localStorage` cache-with-timestamp fallback and a "paste/type it in yourself" manual fallback, and must never render a hard error state; degrade to stale-cache or manual-entry instead. If the own proxy ever needs a new allowed host, edit `ALLOWED_HOSTS` in `functions/api/proxy.js` (deploys with the site). If public proxies break again, check each candidate's live status via WebSearch before wiring it in (a proxy can look fine in search results yet fail with `ERR_NAME_NOT_RESOLVED` for real users — regional DNS blocks are common in Thailand).
- **Google Drive sync** (`DriveSync` pattern, repeated per-tool with a different `DRIVE_FILE_NAME`) is opt-in, best-effort backup of a tool's local data to the user's own Drive — not a sync-of-record.
- **Firebase is gone** (budget data lives in D1 via `tanot-data.js`): `firebase-sync.js`, `ai-summary-cache.js` and `vendor/firebase` were deleted 2026-10-02. `database.rules.json` at the root is a leftover mirror of the Firebase Console rules (project `tanot-budget`) kept for history only — never touch the `tanot-budget*` data or `budget:*` keys.
- **Risk/finance tools carry real disclaimers** — these are educational calculators, not financial advice, and the copy says so explicitly. Preserve that framing when extending them.
- **No explainer clutter in the UI — absolute rule, not a default, applies to every page in this repo, not just `invest-*`.** Never add a "เรียนรู้"/"Learn" accordion card, a head-sub subtitle line under the `<h1>`, a disclaimer paragraph, a static hint/caption span next to a button or input row explaining how to use it, a keyboard-shortcut/mouse-gesture cheat-sheet paragraph, "how this works" narration, step-by-step walkthroughs, or any other explanation of a function/feature into a page's visible copy **unless the user explicitly asks for it in that message**. This is not "use judgment about how much to explain" — it is "write zero explanatory copy by default, every time, on every page, including brand-new pages and pages you are only touching for an unrelated reason (e.g. a layout change) — check for this content and remove it on sight even if removing it wasn't the task you were asked to do." Every `invest-*` page had its head-sub subtitle, "เรียนรู้"/"Learn" lesson accordion(s), and footer disclaimer paragraph deliberately stripped out (Sept 2026, one commit per page — see git log), and `cad.html`/`cad.js` got the same sweep (Sept 2026): head-sub subtitle, the `.cad-precise-hint` spans next to every precise-input row (distance/angle, array, text, hatch, block-insert), the "draw a closed shape then click this" hint under the quick-extrude button, the keyboard/mouse cheat-sheet paragraph at the bottom of the 2D panel, the constraint-panel and plot-panel hint paragraphs, the "Stage 9 (proof of concept)" warn-note banner, and four instructional paragraphs in the 3D panel (add-shape workflow, steps-list workflow, 3D-viewport controls, export-format explainer) — along with roughly two dozen fully orphaned/unused `*Hint` i18n keys that were dead code left over from an earlier iteration. Do not reintroduce any of this, even a shortened version, even if it seems genuinely helpful, on any page, unless the user explicitly instructs you to add it back in that message. This does not apply to dynamic, state-dependent feedback that only exists because of what the user is doing right now (a "click the first corner" prompt during an active multi-click sketch, a validation error, an empty-state message, a live warning that only appears when a real problem is detected) — that stays, because it's functional feedback, not a static tip. The one other narrow exception that survived the sweep is a card that carries live functional data rather than static explanation (e.g. the gold page's factors card with its DXY/TNX price chips, or the business page's reference-ideas list) — those stay because removing them would delete a feature, not an explanation; anything that is purely descriptive text about how a tool works still goes. Where a tool genuinely needs a one-line risk disclaimer and the user has asked for that framing, keep it to one short line; anything longer describing internals (e.g. "this score is a simple heuristic that does X, Y, Z...") gets cut entirely, not shortened-in-place. When in doubt, delete the sentence rather than trim it or keep it "just in case."

### Cloudflare Pages backend (`wrangler.toml`, `functions/api/*`, `migrations/*`)
The Cloudflare Pages deploy (not GitHub Pages) has server code: **Pages Functions** under `functions/api/` (only `/api/*` invokes them; everything else stays static). `wrangler.toml` at the root is the source of truth for Pages config — once it exists Cloudflare **ignores** the bindings and plain-text vars set in the dashboard, so `OWNER_EMAIL` / `ACCESS_AUD` / `TEAM_DOMAIN` live in its `[vars]`, plus bindings `DB` (D1 `tanot-db`), `FILES` (R2 `tanot-files`), `AI` (Workers AI). **Secrets (`ANTHROPIC_API_KEY`) stay dashboard-only — never put a secret in `wrangler.toml` or any file; the repo is public.** **Never add a root `package.json`** (Pages would run `npm install` on every build) — which is also why Functions call the Anthropic API with plain `fetch` rather than the SDK.
- **Auth**: Cloudflare Access (Zero Trust, owner's email only) guards the whole `my-web-app-5w2.pages.dev` domain. `functions/api/_middleware.js` re-verifies the Access JWT on every `/api/*` request (signature via `https://<TEAM_DOMAIN>/cdn-cgi/access/certs`, `aud`, `iss`, expiry, email == `OWNER_EMAIL`) and fails closed, so paid endpoints don't depend solely on dashboard config. There are no client-side passwords for paid features any more.
- **Endpoints**: `proxy.js` (CORS proxy, GET), `ai/chat.js` · `ai/summarize.js` · `ai/embed.js` · `ai/usage.js` (Workers AI — see "Cloud AI" below), `asr.js` (Whisper via `env.AI`), `ocr.js` (Claude Vision OCR — its transcription prompt is deliberately strict about *not* fixing typos; keep it verbatim), `files.js` (R2 `FILES` + D1 `files` index: `POST ?ns=&ref=&name=` raw body → `{id,name,size,mime}`, `GET ?id=` stream, `DELETE ?id=`; allowlist PDF/images, ≤15 MiB, `ns` must be listed in `NAMESPACES` — currently `insurance`, `maintenance`, `health`, `receipts`, `compare`, `slides`, `recipes`, `car`; mutating calls reject a foreign `Origin`; client gates on `*.pages.dev` or `window.TANOT_FILES={enabled}` for tests), `session.js` (used by `sw.js` to tell an Access-expired redirect apart from Pages' own `.html` → clean-URL redirects), `push/*` (Web Push — see below). Original hand-deployed Worker sources are in `docs/*-original.js` for reference only.
- **Pages-only features**: `/api/*` doesn't exist on GitHub Pages, so client code gates cloud features on `/\.pages\.dev$/.test(location.hostname)` and hides the option elsewhere (see `doc-check.js`, `text-to-speech.js`).
- **`sw.js` + Access**: never cache/intercept `/api/` or `/cdn-cgi/`; only cache `ok` + `basic` HTML; on an Access-expired navigation serve the cached page with a "re-login" bar (link carries `?relogin=1`, which the SW passes straight to the network). Manifest links use `crossorigin="use-credentials"` so the manifest fetch carries the Access cookie.
- **D1 schema**: `migrations/0001_init.sql` (idempotent `IF NOT EXISTS`, pasted into the D1 console by the owner) + `0002_push.sql` (`reminders.kind`). Add schema changes as new numbered files; never edit an applied migration — and tell the owner to run the new file in the D1 console (nothing applies migrations automatically). `tests/sync-server.mjs` runs every file in `migrations/` in order.

### Web Push + reminders (ROADMAP Phase 3 / 0a-6: `tanot-push.js`, `notifications.html`, `functions/api/push/*`, `functions/_lib/{webpush,reminders,push,scheduler}.js`, `workers/scheduler/`)
- **Keys**: `VAPID_PUBLIC_KEY` (+ `VAPID_SUBJECT`) in `[vars]` of **both** `wrangler.toml` (root, Pages) and `workers/scheduler/wrangler.toml` — must be identical. `VAPID_PRIVATE_KEY` is a dashboard **Secret** on both the Pages project and the `tanot-scheduler` Worker; never in any file. Owner generates the pair locally with `node workers/scheduler/gen-vapid.mjs`. Empty public key = `/api/push/config` reports `vapid:'missing'` and the subscribe button hides. Owner setup steps: ROADMAP "สิ่งที่เจ้าของต้องทำเอง" ข้อ 7.
- **Crypto** is hand-written WebCrypto (`functions/_lib/webpush.js`: VAPID ES256 JWT + RFC 8291 aes128gcm, no library, nothing to add to `credits.html`). `validEndpoint()` only accepts https endpoints of the browser push services (FCM/Mozilla/Apple/WNS) — the endpoint is user-supplied, so this is the SSRF guard; `PUSH_DEV_ENDPOINT` is a test-only override set by `tests/sync-server.mjs`, never in production config.
- **Endpoints** (behind `_middleware.js`; mutating calls reject a foreign `Origin`): `GET config[?endpoint=]`, `POST subscribe|unsubscribe|test`, `GET|POST reminders`. Table `push_subs` = one row per browser; 404/410 from the push service or 10 consecutive failures delete the row.
- **Reminders** (`reminders` table): a page calls `TanotPush.setReminders(scope, items)` with the **complete set** for its scope every time its data changes; the server replaces the scope (rows not in the set are deleted), writes only changed rows, and keeps `sent_at` when `due_at` is unchanged (so re-registering never re-sends). The client skips the POST when the set's hash is unchanged and < 6 h old (`tanot:push:sent`, `cache` kind in `data-registry.js`). Registration works without this device being subscribed (another device receives). Item builders live in each page's pure calc file, never in the page: `InsuranceCalc.reminders` (scope `insurance`), `TaxCalc.reminders` (scope `tax`, dates only from `tax-rules/*.json` `deadlines`), `MntCalc.digest` (scope `maintenance`), `ReceiptsCalc.reminders` (scope `receipts`), `CarCalc.reminders` (scope `car`). New source = add a builder + scope; `url` must be a page of this site (`foo.html[#…]`, enforced by `cleanItems`).
- **kinds**: `'push'` = one notification at `due_at` (builders use 08:00 Thai time via `Date.UTC(y, m, d, 1, 0)` — never local-time `new Date(y, m, d, 8)`); `'digest'` = one line in the 07:00 Thai daily summary of the day its `due_at` falls on (maintenance: one row per day for the next 14 days, counts only — never per asset). All day boundaries are Thai time (UTC+7) — use `ictDate/ictDayStart/ictAt` from `functions/_lib/reminders.js`, not UTC dates.
- **Scheduler Worker** (`workers/scheduler/index.js`, deployed by Workers Builds with root dir `workers/scheduler`, `workers_dev = false`): `*/15 * * * *` → `runTick` (send due `push` rows; overdue > 2 days are closed without sending; `repeat` rows advance past `now`; all-fail = retry next tick), `0 0 * * *` (07:00 Thai) → `runDaily` (digest, cleanup, D1 → R2 `backups/d1/<Thai date>.json.gz`, 30 days kept). It imports `functions/_lib/scheduler.js`, so editing `functions/_lib/*` also needs a Worker redeploy. Free Workers = 10 ms CPU per invocation; watch the Worker logs if the backup grows.
- **iPhone**: Web Push only works in a home-screen app (iOS 16.4+). `TanotPush.support()` returns `'ios-install'` in Safari and the page hides the subscribe button; `Notification.requestPermission()` must stay the first call inside the click handler (iOS refuses it after an awaited network call).
- **`sw.js`**: `push` → `showNotification` (payload `{title, body, url, tag}`); `notificationclick` → focus/navigate an open tab of the same page (Pages strips `.html`, compare without it) or `openWindow`; any URL outside the SW scope falls back to `index.html`; `pushsubscriptionchange` re-posts to `/api/push/subscribe`.

### Cloud AI (ROADMAP Phase 4: `ai-client.js`, `functions/api/ai/*`, `functions/_lib/ai.js`)

### Data layer / sync (ROADMAP Phase 1: `data-registry.js`, `tanot-data.js`, `functions/api/sync.js`)
Every page loads `<script src="data-registry.js"></script><script src="tanot-data.js"></script>` right after `theme-boot.js` in `<head>`, not deferred (enforced by `tests/repo-guards.mjs`). Page data stays where it always was (localStorage / the page's own IndexedDB); `tanot-data.js` patches `Storage.prototype` and `IDBObjectStore.prototype` to track changes and syncs diffs with D1 `docs` via `GET/POST /api/sync` (last-write-wins per doc, max 40 docs per POST). It is **inert everywhere except `*.pages.dev`** (tests enable it with `window.TANOT_SYNC = { enabled: true }`).
- **Adding a new storage key**: add a rule in `data-registry.js` - `kind: 'sync' | 'local' | 'cache'`; for sync, `mode: 'blob'` (default), `'list'` (JSON array of objects with a unique `idField` - concurrent adds from two devices merge) or `'map'` (JSON object, one doc per property). Anything holding an API key the UI promises stays on-device must be `'local'`. Unmatched keys default to `'local'`. New IndexedDB stores go in `IDB` with the exact schema the page creates; never list an `autoIncrement` store in `sync` (each device counts 1,2,3… so different records collide on the same id - `idbSynced()` refuses them; `report-dashboard`'s `reports` is migrate/backup-only for this reason).
- Safety rules the code relies on (don't break them): a page writing stale in-memory state is 3-way merged at `setItem` (list/map keys) so it can't delete items that arrived from another device; `IDBObjectStore.clear()` on a synced store puts back any record that was in the store but that this page never read (`getAll`) or wrote - e.g. one another tab pulled in; any never-synced/unsynced local value replaced by a remote one is copied to the `history` store (restorable on `data.html`); `localStorage.clear()` and "most keys vanished at once" never produce tombstones - they trigger a re-pull instead; imports (`migrate.html`, `data.html`) never write until the user presses import, stash the imported snapshot + every replaced value first, then read back and verify.
- The dirty queue (`localStorage['tanot-sync:dirty']`) is shared by all tabs: always read-modify-write it, never cache it in memory, and only clear an entry if its timestamp is unchanged since you read it.
- `migrate.html` (pages.dev) opens `migrate-export.html` on github.io as a **popup** (not iframe - storage partitioning) and receives a snapshot via origin-pinned `postMessage`. The export side is read-only; it only adds a `tanot:migrate:exported` marker.
- `drive-backup.js` = one daily snapshot file in Drive (`OME_Progress/tanot-backup-YYYY-MM-DD-<device>.json`, one per device so two devices backing up the same day don't overwrite each other), same format as the migration snapshot. The per-page DriveSync copies stay.
- Read API for aggregate pages: `TanotData.read(key, dflt)` (parsed JSON), `raw(key)`, `readIdb(db, store, {last:N})` (no write tracking, `[]` if the DB/store doesn't exist; `last` reads only the N newest records via cursor) and `onChange(fn)` — use these instead of `localStorage.getItem` so reading a key doesn't count as "the page read it" (which would pop the reload bar when remote data arrives).
- Insurance (`insurance.html`/`insurance.js`/`insurance-calc.js`): policies live in `tanot:insurance:policies` (sync list); `insurance-calc.js` (UMD, no DOM) owns renewal-date math and the tax-deduction caps — `index.js` and any future tax page must use it rather than re-deriving; the page also writes `tanot:insurance:taxsummary` (sync blob) for the tax page to read. Policy files are `{id,name,size,mime}` refs into R2 via `/api/files`; deleting a policy/file must also `DELETE` it there.
- Tests: `tests/sync-server.mjs` runs the real `functions/api/sync.js` on `node:sqlite` with `migrations/*.sql`; `sync.spec.js` (2 browser contexts) and `migrate.spec.js` (127.0.0.1 = "github.io", localhost = "pages.dev").

### The 4 React pages (`languages`, `legal`, `classroom-business`, `classroom-engineering` — ROADMAP Phase 2 round 6)
These four are React 18 apps with **no runtime CDN dependency** (Tailwind/React/Babel/lucide all come from the repo, so they open offline). Per page: `<page>.html` (data `<script type="application/json">` blocks such as `course-data`/`legal-templates`/`lang-data` stay in the HTML and are read via `document.getElementById(...).textContent`) + **`<page>.jsx`** (the JSX source you edit) + **`<page>.compiled.js`** (esbuild output, classic `React.createElement` runtime, ES2019, iife — the only file the browser loads). Shared: **`react-pages.css`** (one Tailwind v3 build over all four pages' `.html`/`.jsx`), `vendor/react/` (React/ReactDOM 18.3.1 production UMD, pinned — to bump: `npm pack react@X react-dom@X` and copy `package/umd/*.production.min.js`), `vendor/lucide/lucide.min.js` (lucide 1.49.0 UMD from the pinned `lucide` devDependency; icons are `<i data-lucide>` inside a React-owned span + `lucide.createIcons()`).
- **After editing any of the 4 `.jsx`/`.html` files, or `tests/react-build/*`, run `./build-react.sh` and commit the regenerated `*.compiled.js` + `react-pages.css` together.** Editing `.jsx` alone does nothing live — same failure class as forgetting to bump `sw.js` `CACHE`. `./build-languages.sh` is now just an alias. Tools are pinned in `tests/package.json` (`esbuild`, `tailwindcss` 3.4.x, `lucide`): first run `cd tests && npm ci`. Never add a root `package.json`. `tests/repo-guards.mjs` fails if a compiled file or the CSS is stale, or if a page references cdn.tailwindcss.com/unpkg/Babel again.
- **Tailwind ↔ theme tokens** (`tests/react-build/tailwind.config.js`): every colour is bound to a `--ome-*` token (`bg-white`→card, `bg-slate/gray-50`→bg, `text-slate-800`→ink, `text-slate-400/500`→muted, `border-slate-200`→line, `brand`/`primary`/`secondary` → brand tokens, `shadow-*`→`--ome-sh`, `font-sans`→`--ome-f`; `bg-primary`/`from-primary` use `--rp-fill-*` so white text stays legible in dark mode; opacity modifiers like `bg-brand/10` work via `color-mix`). So light/dark/accent/font switching needs no `!important` overrides in `theme.css` — **never re-add `.ome-app-page …` rules there; change the config instead**. New class on a page = just rebuild. Semantic colours not listed (e.g. `text-red-600`, `bg-amber-100`) stay Tailwind defaults. Class names must appear literally in the source (no `` `bg-${x}` ``) or Tailwind will not generate them.
- `react-pages.css` is unlayered and loaded after `theme.css`, so Tailwind preflight/utilities beat the layered `data-layout` base (`input.css` re-inherits heading colour/line-height for that reason). Bodies are `data-layout="reader"` (the two classrooms) / `"tool"` (languages, legal); don't use `"app"` (it locks the body to 100dvh).
- Script order: `vendor/react/*` + `vendor/lucide` in `<head>` (plain), then the compiled page script (`defer` on the 3 smaller pages so it runs after `shell.js`; `languages.compiled.js` is a plain script at the end of `<body>`). Still loaded from the network by design (optional features, never needed to open a page): `tesseract.js` + `hanzi-writer` (jsDelivr; handwriting mode of `languages`), Google Identity (Drive sync), Google Fonts.
- `sw.js` PRECACHEs the compiled JS, `react-pages.css` and the vendor files — bump `CACHE` when any of them change.

### Heavy client-side ML (`text-to-speech.html` / `text-to-speech.js` / `tts-worker.js`)
Text→speech uses `facebook/mms-tts-*` via `vendor/transformers/` (Transformers.js + onnxruntime-web, self-hosted, not CDN-loaded — a prior CDN-based bare-specifier resolution bug inside a Worker is why the vendored bundle's imports were rewritten to relative paths). The onnxruntime-web runtime files (`ort-wasm-simd-threaded*.mjs/.wasm`, `ort.webgpu.bundle.min.mjs`, `onnxruntime-common/*`) are **pinned to 1.24.3** on purpose — 1.25+ has a confirmed upstream bug (`TransposeDQWeightsForMatMulNBits`, microsoft/onnxruntime#28306) that breaks session creation for some quantized models including Whisper. Don't bump these without first confirming that issue is fixed in the target version. Synthesis runs in a **pool of persistent Web Workers** (`tts-worker.js`, spawned via `getTtsWorkerPool()`), not the main thread, because single-thread WASM synthesis is fully synchronous and would otherwise freeze the page. Key things that look like they'd be free performance wins but were tried and reverted after real-world measurement: WebGPU backend (slower — immature quantized-op kernels), multi-threaded WASM via COOP/COEP cross-origin isolation (slower/same — thread oversubscription across the worker pool). The one that *did* help: staggering worker dispatch so only the first worker downloads the model initially (`pipeline-ready` message), avoiding N workers redundantly re-downloading the same multi-MB model on a cold cache. Speech→text uses Whisper, also via Transformers.js.
