> ไฟล์นี้เป็นบันทึกภายในสำหรับผู้พัฒนา (พี่ + Claude) เท่านั้น ไม่ได้ถูกอ้างอิงจาก
> HTML/JS ของเว็บจริง ไม่กระทบผู้เข้าชมเว็บ — เก็บไว้ให้ session ถัดไปอ่านต่อได้
> แม้ scratchpad ของ session เดิมจะหายไปแล้ว (เพราะ container เป็น ephemeral)

สถานะ ณ ตอนเขียน (หลังทำหัวข้อ 1-12 ของวิชานิติกรรมสัญญาเสร็จ กำลังเตรียม 14-15):
เนื้อหาบทเรียนเริ่มเยอะและยาวขึ้นเรื่อยๆ พี่เลยขอให้ช่วย brainstorm วิธีนำเสนอ/
เครื่องมือเพิ่มเติม สรุปไอเดียทั้งหมดที่คุยกันไว้ด้านล่าง (ยังไม่ได้เริ่มทำจริงสักข้อ
รอพี่ยืนยันตอนเปิด session ใหม่)

## 1. UX/การนำทาง (เร่งด่วนสุด เพราะกระทบการอ่านเนื้อหาที่มีอยู่แล้วโดยตรง) — ✅ ทำเสร็จแล้ว
1. ✅ **สารบัญหัวข้อแบบ chip** บนสุดของการ์ดบทเรียน — กดแล้วเลื่อน+เปิดหัวข้อนั้นทันที
   (implement: `.lchips`/`.lchip` ใน classroom-law.js `renderLessonContent()`)
2. ✅ **จัดกลุ่มเป็น "ภาค"** ตามเนื้อหาจริง (ภาคนิติกรรม = หัวข้อ 1-8, ภาคสัญญา = หัวข้อ
   9-15) ผ่าน metadata `LESSON_CONTENT.nitikam.groups` (ใช้ `count` สะสมจาก `parts`
   — ถ้าเพิ่มหัวข้อใหม่ภายหลังต้องอัปเดต `count` ให้ตรงด้วย) — วิชาอื่นที่ไม่มี
   `groups` จะ fallback เป็นรายการเรียบ (flat) อัตโนมัติ
3. ✅ **ติ๊กว่าอ่านแล้ว** ต่อหัวข้อ (เก็บใน `localStorage` คีย์ `tanot:barprep:lessonread`
   โดยใช้ชื่อหัวข้อ/title เป็นคีย์ย่อย ไม่ใช่ index — กันปัญหาถ้าลำดับหัวข้อเปลี่ยนภายหลัง)
   + progress bar % ของวิชา (`.lprog`/`.lprog-fill`)
4. ✅ **ข้อสอบจัดกลุ่มตามหัวข้อ** — เพิ่มฟิลด์ `topic: N` ให้ข้อสอบ nitikam ทั้ง 47 ข้อ
   (map เทียบจากเนื้อหา/เลขมาตราที่อ้างในแต่ละข้อ ไล่ตรวจเทียบด้วยมือ ไม่ใช่ auto 100%
   — ถ้าพบข้อไหนจัดหมวดผิดพลาดภายหลัง แก้ที่ฟิลด์ `topic` ของข้อนั้นได้เลยใน
   `EXAM_QUESTIONS.nitikam`) จัดกลุ่มแสดงผลผ่าน `NITIKAM_TOPIC_LABEL` +
   กล่องค้นหา/กรองด้วยคำสำคัญหรือเลขมาตรา (`#exqSearch`) และ dropdown กรองตามหัวข้อ
   (`#exqTopicFilter`) ใน `renderExamQuestions()` — วิชาอื่นที่ไม่มี `topic` fallback
   เป็นรายการเรียบพร้อมช่องค้นหาเฉยๆ (ไม่มี dropdown หัวข้อ)

ทดสอบแล้วด้วย Playwright (headless Chromium) ผ่าน local http server — chip
คลิกแล้วเปิด+เลื่อนถูกหัวข้อ, ติ๊กอ่านแล้วอัปเดต progress bar ถูกต้องและไม่ปิด
หัวข้อที่เปิดค้างอยู่, ค้นหา/กรองข้อสอบทำงานถูกต้อง (ทดสอบทั้งค้นคำ, ค้นเลขมาตรา,
กรองตามหัวข้อ, และ empty-state เมื่อค้นไม่เจอ) ไม่มี JS error ขึ้น deploy แล้ว
(sw.js v143)

## 2. เครื่องมือการเรียน (เพิ่ม) — ข้อ 5-11 ทำเสร็จแล้ว ✅ (เหลือ 12)
5. ✅ **โหมดทำข้อสอบจริง (Mock Exam)** — การ์ด "🧪 ข้อสอบจำลอง" ใหม่ในหน้าวิชา สุ่ม N ข้อ
   จากธนาคาร `EXAM_QUESTIONS` จับเวลานับขึ้น ไม่เปิดเฉลยระหว่างทำ ต้องทำครบชุดก่อนถึงจะ
   เห็นแนวคำตอบทั้งหมด + เวลารวมที่ใช้ (ฟังก์ชัน `startMockExam`/`renderMockQuestion`/
   `finishMockExam` ใน classroom-law.js)
6. ✅ **Auto-flashcard จากเนื้อหาบทเรียน** — ปุ่ม "⚡ สร้าง flashcard จากคำที่ขีดเน้นใน
   บทเรียน" ในการ์ดสมุดโน้ต ดึงคำที่ทำ `==เน้น==` ไว้ทุกจุดในสรุปเนื้อหาของวิชาที่เลือก
   มาเป็นการ์ดหน้า-หลังอัตโนมัติ กันซ้ำด้วยคีย์ subj+q (`extractHighlightFlashcards`/
   `autoFlashFromHighlights`)
7. ✅ **อัปเกรด SRS เป็น FSRS** — เปลี่ยนจากขั้นบันไดตายตัว `[1,3,7,14,30]` วัน เป็นโมเดล
   stability/difficulty ต่อการ์ด + สูตร forgetting curve จริงของ FSRS (`R=(1+t/9S)⁻¹`
   เป้าความจำ 90%) ปุ่มให้คะแนนเปลี่ยนจาก 2 ปุ่ม (จำได้/จำไม่ได้) เป็น 4 ปุ่มแบบ Anki
   (Again/Hard/Good/Easy) — พารามิเตอร์การเติบโตของ stability เป็นแบบย่อที่ออกแบบเอง
   ให้ทำงานถูกต้องตามหลักการ ไม่ใช่ค่าพารามิเตอร์ต้นฉบับที่ optimize จากข้อมูลจริงของ
   Anki (ดูคอมเมนต์ในโค้ดเหนือ `fsrsSchedule()`) กราฟ "ตารางทบทวน SRS" ในแดชบอร์ด
   ปรับ bucket ให้จัดกลุ่มตาม stability แทน srsIdx เดิมแล้ว
8. ✅ **ดัชนีค้นมาตรา** + 9. ✅ **คลังฎีการวม** — รวมเป็นเครื่องมือเดียว "🔎 ค้นหามาตรา/ฎีกา
   (ทุกวิชา)" อยู่บนสุดของหน้าวิชา (เห็นตลอดไม่ต้องรอเลือกวิชา) ค้นข้อความแบบเดียวกัน
   ทั้งเลขมาตราและเลขฎีกา/คำสำคัญ กวาดทั้ง `LESSON_CONTENT` และ `EXAM_QUESTIONS` ของ
   ทุกวิชา ไฮไลต์คำที่เจอ + ปุ่ม "ไปดู →" กระโดดไปเปิดหัวข้อ/ข้อสอบต้นทางให้เลย
   (`buildReferenceHaystack`/`renderRefSearchResults`)
10. ✅ **โหมดฝึกจำเลขมาตรา (drill สั้นๆ)** — การ์ด "⚡ ฝึกจำเลขมาตรา" สุ่มโจทย์สถานการณ์
    สั้นจากธนาคาร `DRILL_QUESTIONS.nitikam` (เขียนเอง 16 ข้อ ครอบคลุมหัวข้อ 1-12,14,15)
    กดดูเฉลยแล้ว self-report ถูก/ผิดเอง วนซ้ำได้ไม่รู้จบ (`startDrill`/
    `renderDrillQuestion`) — วิชาอื่นที่ยังไม่มีธนาคาร drill จะซ่อนการ์ดนี้ไปอัตโนมัติ
11. ✅ **ไฮไลต์/จดโน้ตส่วนตัวลงในเนื้อหาบทเรียนโดยตรง** — ปุ่ม "📝 โน้ต" ในแต่ละหัวข้อ
    บทเรียน เปิด textarea ผูกกับ `localStorage` คีย์ `tanot:barprep:lessonnote`
    (ใช้ชื่อหัวข้อเป็นคีย์เหมือนระบบ "อ่านแล้ว") บันทึกอัตโนมัติทุกครั้งที่พิมพ์ —
    ตัดสินใจไม่ทำ true text-selection highlighting (เลือกคำแล้วไฮไลต์ในเนื้อหาโดยตรง)
    เพราะต้องใช้ Range/Selection API ที่เปราะบางเมื่อเนื้อหาเปลี่ยน เลือกวิธีนี้แทน
    เพราะทนทานกว่าและยังตอบโจทย์ "ลดขั้นตอนเทียบกับสมุดโน้ตแยกการ์ด" ได้

ทดสอบทั้ง 6 ข้อ (5-11, ข้อ 7 ทดสอบผ่านการรีวิว/ให้คะแนน FSRS จริง) ด้วย Playwright
(headless Chromium) ผ่าน local http server แล้ว ไม่มี JS error เลย — deploy แล้ว
(sw.js v144)

12. ✅ **Export เป็น PDF ต่อวิชา** — ปุ่ม "📄 Export PDF ทั้งวิชา" ในหัวการ์ดสรุปเนื้อหา
    ใช้ html2canvas+jsPDF (ตัวเดียวกับ word.html/excel.html ใช้อยู่แล้ว โหลดผ่าน CDN
    เพิ่มใน classroom-law.html) — render เนื้อหาทั้งวิชาลงกล่องซ่อนไว้กว้าง A4 (794px)
    แล้ว capture เป็นภาพต่อเนื่องตัดแบ่งหน้า A4 เอง ต่างจาก word.js ตรงไม่ต้องคุมหลาย
    ขนาดกระดาษเพราะเป็นเอกสารไหลต่อเนื่องหน้าเดียว (`exportSubjectPdf()`) — ถ้าโหลด
    CDN ไม่ได้ (ออฟไลน์) fallback เป็น `window.print()` แทน มีข้อความแจ้งชัดเจน

    browser) ยืนยันว่าตัดสัญลักษณ์ markdown ออกหมดจริง และจัดการ edge case (ข้อความว่าง/

16. ✅ ปุ่มเล่น/หยุดชั่วคราว/หยุด/ข้ามหัวข้อถัดไป-ก่อนหน้า (โหมด playlist เท่านั้น) — มีตัว
    กันการแข่งกันของ event แบบ async (`ttsGen` counter) ตอนกดข้ามเร็วๆ ไม่ให้เสียงซ้อนกัน
17. ⚠️ **เปลี่ยนแนวทางจากแผนเดิม**: แผนเดิมจะ "ต่อยอดจากระบบ TTS ที่มีอยู่แล้วในเว็บ"
    (text-to-speech.js/tts-worker.js) ซึ่งใช้โมเดล MMS-TTS แบบดาวน์โหลด/สร้างไฟล์เสียง
    ก่อนถึงจะฟังได้ (ใช้เวลาหลายวินาทีถึงหลายนาทีต่อครั้ง) — **เปลี่ยนไปใช้ Web Speech API
    ของเบราว์เซอร์แทน** (`window.speechSynthesis`) เพราะเล่นได้ทันทีไม่ต้องรอ ตรงกับที่
    ต้องการจริงๆ คือ "ฟังตอนออกกำลัง/เดินทาง" และ**ข้ามปัญหาบั๊ก "หน้าเว็บรีเฟรชเอง" ที่
    สงสัยว่าเกี่ยวข้องกับเสียง "หญิง (โทนพอดแคสต์)" ไปได้ตั้งแต่ต้นเลย** เพราะเป็นคนละ
    ระบบเสียงกับโมเดล MMS-TTS ของ text-to-speech.html โดยสิ้นเชิง ไม่ได้เรียกใช้โมเดลนั้น
    เลย — ค่าเริ่มต้นเลือกเสียงภาษาไทยทั่วไปของเบราว์เซอร์/อุปกรณ์เอง (ผู้ใช้เปลี่ยนเสียง
    อื่นที่มีในเครื่องได้เองจาก dropdown เก็บค่าที่เลือกไว้ใน localStorage)
    **บั๊ก "หน้าเว็บรีเฟรชเอง" ของโมเดล MMS-TTS เดิมยังไม่ได้แก้/ตรวจสอบ** (ยังเลื่อนไว้ทำ
    หลังสุดเหมือนเดิมตามที่ขอไว้แต่ต้น session — แค่ฟีเจอร์ใหม่นี้ไม่เกี่ยวข้องกับมันแล้ว)

ทดสอบข้อ 12-16 ด้วย Playwright (headless) แล้ว — สภาพแวดล้อมทดสอบไม่มีเสียง TTS จริง
(ปกติของ headless sandbox) ทำให้ทดสอบเสียงจริงไม่ได้ แต่ยืนยันว่าไม่มี JS error ตลอดทุก
ปุ่ม/ทุกสถานะ (รวมกดรัวๆ ทดสอบ race condition) และ dropdown เลือกเสียงทำงานถูกต้อง (จำลอง

   แครชเพราะหน่วยความจำ WASM ไม่พอ (เบราว์เซอร์กู้คืนด้วยการโหลดหน้าใหม่ = ดูเหมือนหน้า
   รีเฟรชเอง) — **แก้แล้ว**: sync `tts-worker.js` ให้ตรงกับ `text-to-speech.js` (เหลือแค่
   เสียง "โทนพอดแคสต์" เท่านั้นที่ยังบังคับ fp32 จริง เพราะไม่มีไฟล์ quantized ให้เลือกเลย)
   เพิ่ม comment เตือนชัดเจนในทั้ง 2 ไฟล์ว่าต้องแก้คู่กันเสมอ (ไม่มี module กลางให้ import
   ร่วมได้ตรงๆ เพราะคนละ execution context — main thread vs Worker)
2. **โมเดลแชท AI ตัวใหญ่ (1.5B ผ่าน WebGPU) ไม่เช็ก VRAM ก่อนลอง** — `ai-chat-worker.js`
   เดิมลองโหลดโมเดล 1.5B ผ่าน WebGPU ทันทีที่เจอ `navigator.gpu` (แค่บอกว่าเบราว์เซอร์/
   ไดรเวอร์รองรับ WebGPU เฉยๆ ไม่ได้บอกว่าการ์ดจอมี VRAM พอจริง) — ถ้าโหลด pipeline สำเร็จ
   แต่ "พังตอน generate จริง" (VRAM ไม่พอกลางคัน) มักเป็น GPU process crash ที่ JS
   try/catch หรือ Promise.catch() ดักจับไม่ได้เลย (ต่างจากตอนโหลดพังที่ยัง reject เป็น
   error ให้ดักได้ปกติ) ตรงกับอาการที่พี่เจอ ("ถามผู้ช่วย AI แล้ว รอ load เสร็จ หน้าเว็บ
   refresh auto" — คือพังตอน**หลัง**โหลดเสร็จแล้วเริ่ม generate จริง ไม่ใช่ตอนโหลด) —
   **แก้แล้ว**: เพิ่มเงื่อนไข `navigator.deviceMemory >= 4` (ยืนยันแรมเยอะพอจริง) ก่อนจะ
   ลองโมเดลใหญ่ ใช้เกณฑ์เดียวกับ `ttsPoolSize()` ที่แก้บั๊ก iOS OOM ไปแล้วก่อนหน้านี้
   (ระมัดระวังไว้ก่อนเมื่อไม่รู้ค่า — iOS Safari ทั้งหมดได้ค่า undefined เสมอ) แลกกับ
   คำตอบที่อาจไม่ดีเท่าโมเดลใหญ่บนเครื่องที่ไม่รู้ค่าจริงๆ แต่แรงพอ เพื่อความเสถียรเป็นหลัก
